## How to run

**Setup:** `pip install -r requirements.txt`; transcribing audio also needs `ffmpeg`

**Layout**
- `src/`: the pipeline. `main.py` runs it: load and clean the messages (`load_dataset.py`, `preprocess.py`), redact
  personal information (`redact.py`), label each message Event or Chit-chat and each Event's activity (`relevance.py`,
  `extract.py`), build the output tables (`tables.py`) and write the report (`summarize.py`). `transcribe.py` turns
  voice notes into text first.
- `eval/`: evaluation scripts
- `tools/`: data preparation
- `data/`: inputs and labeled dev sets
- `results/old/`: outputs of earlier versions

**Run**
```bash
# 1. Voice notes -> transcripts (skip for text exports)
python src/transcribe.py data/voice_notes/ -o data/voice_notes.csv --hints "Rongai, Nakuru"
# 2. Messages -> outputs/<name>/messages.csv, follow_ups.csv, and with -s, report.md
python src/main.py -d data/hidden_test_transcripts.xlsx -o outputs/hidden_test --extract_info --filter_relevant -s Qwen/Qwen2.5-7B-Instruct
# OR load from a Huggingface dataset instead of a local file
python src/main.py -d ChristianCaballero/WhatsApp-style-Conversations-Ar-En-Zh-Ko-Logs-Pack -o outputs/hidden_test --extract_info --filter_relevant -s Qwen/Qwen2.5-7B-Instruct
```
The tables run on a CPU in a few minutes without `-s`. The report needs a GPU; the 7B summarizer also needs about
32 GB of RAM (on WAVE, request it when starting the session). With `-s Qwen/Qwen3-0.6B` it fits a small GPU, but the
report is much worse: on the hidden test, faithfulness 0.50 and completeness 0.50 against 0.70 and 0.83 for the 7B
(see `results/README.md`).

`messages.csv` has one row per message: anonymized text (`Person0` / `Place0` aliases, `[PHONE]` / `[EMAIL]` tags),
Event or Chit-chat (relevant or not), activity type, head count, duplicates, sensitive topic, and a confidence with the reasons to
review the row. `follow_ups.csv` lists the sentences that ask someone to act.

**Evaluate**
```bash
python eval/eval_hidden_test.py -p outputs/hidden_test/messages.csv   # against the hidden-test key
python eval/eval_relevance.py                                         # Event / Chit-chat on the dev set, hidden test, FarmerChat
python eval/eval_extraction.py                                        # activity type and head count
python eval/pii_eval.py -n 200                                        # redaction recall (ai4privacy)
python eval/eval_summary.py -r outputs/hidden_test/report.md -m outputs/hidden_test/messages.csv   # report faithfulness, completeness, conciseness
python eval/eval_asr.py -m openai/whisper-small                       # speech-recognition WER
```
The dev sets (`data/relevance_dev.jsonl`, `data/extraction_dev.jsonl`, made by `tools/make_dev_sets.py`) are generated by Qwen,
but they have a field (`reviewed_by_human`) we can mark off after manually verifying the labels. The dev sets were generated considering Dandelion's
activities.

### 1. Problem formulation and social impact
- **Problem:**  
Our goal is to convert exported WhatsApp messages and voice recordings into a structured report of activities and outcomes, as well as anonymize any personal information from the exports.
- **Intended users:**  
This system is built for Dandelion Africa with the purpose of making reports of field outcomes. Any other organization who also needs to create reports from internal communications could also use it. Most of this information is going to be used for reports or the creation of easy to read structured data of any activities that have been done.
- **Inputs and outputs:**  
The system will receive chat files or voice notes on WhatsApp and produce structured outputs later that are anonymized. A concrete example would be a worker fixing machinery and reporting the action or outcome on WhatsApp. The system should transform that chat or voice note into a structured report that any supervisor or member of the organization can easily view.
- **Success criteria:**  
The system would be useful and reliable if it writes consistent and useful reports, is able to accurately anonymize personal information, removes any unnecessary information, and correctly identifies important outcomes.
- **Constraints and risks:**  
Constraints we have is having good testable data, context window, dealing with AI hallucinations, human accents, typos, and informal language.

### 2. Proposed technical approach
- **Pipeline:**  
The main steps from input to output depends on if the message is in text or voice note. If it's a voice note, we need to transcribe it first. Then we can classify the the information into personal information, important information, and irrelevant information. Then we can split it off into 3 differnet tasks: anonymizing personal information, structuring important information into reports, and removing irrelevant information.
- **Baseline(s):**  
The simplest end-to-end method is fully blacking out any personal information, taking anything valuable information into an output, and removing irrelevant information. 
- **Proposed models/tools:**  
For text generation: llama 3.1 8B instruct https://huggingface.co/meta-llama/Llama-3.1-8B I selected this because it has a large enough parameter for all the text it will receive and it's an efficient model that can run on the WAVE HPC without taking up too many resources.
For audio to text: Whisper https://github.com/openai/whisper Whisper is one of the best audio to text transcribers and is accurate.
For classification: Bart large mnli https://huggingface.co/facebook/bart-large-mnli It's one of the most downloaded and used classification models on Huggingface. It's also backed by Meta which is a successful name in the AI industry. It has .4 billion parameters, which is more than enough for classifying.
- **Alternative approach:**  
If the baseline underperforms, then we will try and increase model sizes to see if the model's are the ones causing this performance as they're doing most of the heavy work or we can change our training data.

## Week 6 — Build: Working Baseline

**Deliverable during Week 7 Lab:** A runnable baseline, setup/run instructions, and 1–2 example inputs and outputs. Update this section with what worked, what failed, and individual contributions.

### Implementation status
- **What runs end-to-end now?** The program loads a given dataset and scans/redacts personal identifying information following known patterns. For the sake of performance, hyperscan is used instead of the built-in re module. It then passes the text through a sequence-to-sequence model to summarize it. If the input token count is greater than the maximum sequence length, it will split the tokens into blocks and summarize them. This process is repeated with the separate generated summaries until it fits within the maximum sequence length, meaning only a single output sequence is generated. This is the final summary.
- **How to run it:** Use the following command line arguments. -d is required, and no result will be seen if neither -o nor --input_out are specified. -il should be set based on the model used.  
-d or --dataset: Name of the dataset to process, either locally stored or from Huggingface  
-s or --summarizer: Name of the summarization model to use, either locally or from Huggingface  
-l or --length: Minimum length of the summary  
-il or --input_length: Maximum input length in tokens that the summarization model can handle  
-b or --use_blocks: Whether text longer than the max input length should be split and processed in blocks. If this flag is not used, the input will be truncated  
-o or --output: File to write the output summary to  
--input_out: File to write the used (redacted) input text to

The affected users are anyone who have worked with or received help from Dandelion Africa and had their activities recorded. - **Human oversight:** A human should review the generated reports for any leaked PII, read and address the follow-up reports, and validate that the correct events and actions are reported.
- **Remaining limitations:** There is still room for missed redactions (names specifically), incorrectly categorized events, and entries incorrectly being marked relevant or irrelevant. ### Extra credit: going beyond the baseline

The baseline pipeline turns each message into a row of an output table. Three additions go beyond it, aimed at the three extra-credit criteria (originality, social impact and clear presentation of results).

**1. Redaction that survives speech-recognition mistakes (originality)**
Whisper often misspells Kenyan names and places ("Soli" for Solai, "Girissa" for Garissa, "Kampiamoto" for Kampi ya Moto). A list-based redaction misses these, so private names and places stay readable. `src/redact.py` now:
- finds places and people from the sentence around them ("the matatu from Soli", "send it to Ruth", "I was with Grace"), so a misspelled name that no list contains is still hidden;
- matches a misspelled word against our Kenyan place list (`data/kenya_places.txt`, built by `tools/build_place_list.py`) and gives it the same alias as the real place;
- reads each batch twice, so a name introduced in a later message is also hidden in earlier ones;
- records each guess in `pii_notes`, which feeds the review column below.

`src/transcribe.py --hints "Rongai, Nakuru"` also gives Whisper a list of local names. We tried it on one synthetic clip, where it turned "Girissa" into "Garissa". We have not tried it on the real audio.

Result on our own Whisper transcripts of the 10 hidden-test audio files, scored against the TA's table (`eval/eval_hidden_test.py`): expected PII tags found went from 37/46 (recall 0.804, precision 0.974) to 44/46 (recall 0.957, precision 0.978). On our FarmerChat dev set (`data/farmerchat_kenya_labeled.jsonl`), places caught went from 40/64 to 54/64 with no ordinary words hidden. The tables are in `results/hidden_test_fixed/` and `results/old/hidden_test_whisper_metrics.md`.

**2. A review queue with confidence scores (originality, Responsible AI)**
Every row of `messages.csv` has `confidence`, `confidence_level`, `needs_review` and `review_reasons`. Each doubt lowers the confidence: two methods disagreeing on the activity or head count, no head count, a possible duplicate, a place that was guessed or looks misspelled, or a capitalized word still visible after redaction. A person then only has to check the uncertain rows. On the TA's clean transcripts 9 of 10 rows are High confidence and 5 are sent to review (the sensitive ones, a duplicate and a disagreement). On our Whisper transcripts only 2 are High, 7 Medium and 1 Low, and 8 are flagged, with reasons such as a misspelled place or a name left visible. So the queue gets stricter as the input gets noisier, which is what we want.

**3. A follow-up list and protection for sensitive topics (social impact)**
`follow_ups.csv` lists the sentences that ask someone to act: referrals, people to call back, next visits, reports still to send, and supplies that ran out. This turns a chat into the list a supervisor acts on.

Messages about gender-based violence, HIV, screening results and reproductive or mental health get a `sensitive_topic`. They always go to review, and the sentences about one identifiable person (for example a woman with a positive result, and her phone number) are withheld from the report. The summarizer only sees this protected text, and follow-ups about one person in a sensitive message are marked "restricted" for the case owner. In the hidden test, 5 of 10 messages are sensitive (2 reproductive health, 2 screening results, 1 gender-based violence). Names are already hidden, but the health details tied to one person could still identify them, which is why this matters.

**Limits we want to be clear about**
- The keyword lists for sensitive topics and follow-ups, and the redaction rules, were written alongside the hidden test, so the hidden-test scores are in-sample. FarmerChat is the fairer check for places.
- The confidence penalties are hand-set, not calibrated on data.
- Our duplicate rule compares only activity type and head count, so two reports of a recurring event (for example a monthly savings meeting) would be flagged as duplicates. We found this in peer testing; audio files carry no date, so the fix needs timestamps from chat exports.
- The Whisper hint option has not been tested on the real audio.
